# 队伍优先的配置与计算工作区设计

## 目标

将前端从“先选主角色，再补充队友”的单一场景编辑器，重构为两个边界清晰的工作区：

1. 配置页维护角色配置库并组成一支 1–4 人队伍。
2. 计算页从当前队伍中任选一名成员，再选择该成员的指标进行计算。

这次重构只改变前端状态组织和计算请求装配方式，不把角色默认配置的维护工作混入其中。

## 已确认的产品决策

- 同一个角色允许保存多套配置，每套配置由唯一 `buildId` 标识。
- 一支队伍只能包含同一角色的一套配置，但可以随时切换为该角色的另一套配置。
- 队伍由 1–4 名成员构成，不赋予坑位顺序、队长或前台角色等特殊语义。
- 队伍保存在浏览器本地，刷新或重新打开网站后恢复。
- 导出只包含全部角色配置，不包含队伍、敌人、Buff、指标选择和计算结果。
- 不提供单份角色配置导出。
- 配置页和计算页分离；计算页不直接编辑角色配置。
- 武器和圣遗物特效由分析器按照当前角色、队伍和目标动作实际可达到的最大值自动解析。

## 当前问题

当前工作台直接以 `EvaluationScenario.primary` 为中心保存页面状态，并把 `teammates`、指标、配置来源、编辑器和计算结果放在同一个组件中。这导致：

- 用户必须先指定“主角色”，才能导入或创建配置。
- 切换计算对象会交换 `primary` 与 `teammates`，同时改变队伍状态。
- 配置库、队伍和一次计算场景彼此耦合。
- 武器与圣遗物主动效果混入场景勾选项，基准武器与候选武器可能使用不同的效果解析路径。
- 页面左侧流程承担了状态机、导航和编辑器三种职责。

## 信息架构

### 配置页 `/`

页面自上而下分为三块：

1. 配置操作栏
   - 导入展示柜配置
   - 导入 JSON 配置
   - 手动初始化角色配置
   - 导出配置
2. 已配置角色
   - 按角色分组
   - 每组可以包含展示柜、JSON、手动初始化等多套配置
   - 卡片主信息只展示角色官方中文名和配置来源
   - 已入队配置整卡高亮
3. 当前队伍
   - 四个无语义坑位
   - 点击配置卡“入队”时加入第一个空坑位
   - 点击空坑位“+”时为该坑位选择配置
   - 队伍已满时，新增成员必须明确选择被替换成员
   - 切换同角色的另一套配置时，原坑位直接改为新的 `buildId`

确认队伍只负责校验成员数量与角色唯一性，然后进入计算页，不创建角色配置副本。

### 计算页 `/calculate`

页面顶部展示当前队伍的只读摘要。用户按以下顺序操作：

1. 从队伍中选择计算对象。
2. 从该角色已维护的伤害指标和辅助指标中选择一个指标。
3. 配置敌人和 Buff。
4. 开始计算。

角色配置有误时返回配置页修改。计算页不展开完整武器、圣遗物、等级、天赋和命座编辑器。

计算结果按以下固定顺序展示：

1. 指标期望结果
2. 结算面板
3. 结算轨迹
4. 圣遗物有效词条
5. 圣遗物原始值输入
6. 词条增加的边际收益
7. 更换武器收益

辅助指标没有伤害型结果时，仍复用相同的报告容器；不适用的分析区明确标记为不适用，而不是伪造伤害结果。

## 前端状态模型

配置库、队伍和计算会话必须分开持久化和更新：

```ts
interface BuildLibraryState {
  readonly builds: readonly CharacterBuild[]
  readonly schemaVersion: 1
}

interface PartyState {
  readonly memberBuildIds: readonly string[]
}

interface CalculationSessionState {
  readonly buffs: readonly ExternalBuff[]
  readonly enemy: EnemyConfig
  readonly metricId: string | null
  readonly targetBuildId: string | null
}
```

约束：

- `BuildLibraryState.builds` 以 `buildId` 唯一。
- `PartyState.memberBuildIds` 长度为 1–4，且引用必须存在于配置库或已经确认的内置默认配置中。
- 队伍中各配置的 `characterId` 必须唯一。
- 删除一份已入队配置时，同时从队伍中移除该 `buildId`。
- `CalculationSessionState.targetBuildId` 必须属于当前队伍。
- 更换队伍后，如果原计算对象不再存在，则清空计算对象、指标和旧结果。

## 本地存储与导入导出

配置库和队伍使用不同的本地存储键，避免导入配置时覆盖当前队伍：

```text
project-b.build-library.v1
project-b.party.v1
```

工作空间导出结构只承载角色配置：

```ts
interface BuildWorkspaceExport {
  readonly builds: readonly CharacterBuild[]
  readonly exportedAt: string
  readonly schemaVersion: 1
}
```

导入规则：

- 同一 `buildId` 的导入配置覆盖本地配置。
- 不同 `buildId` 的同角色配置并存。
- 导入前完成结构校验和角色配置交叉字段校验。
- 导入失败不修改已有配置库。
- 兼容现有单个 `CharacterBuild`、现有 `EvaluationScenario` 和新的工作空间格式；旧场景只提取其中的角色配置，不导入旧队伍和场景条件。

## 计算请求适配

前端内部不再长期保存 `EvaluationScenario.primary`。发起伤害计算时临时装配：

```ts
const primary = partyBuilds.find((build) => build.buildId === targetBuildId)
const teammates = partyBuilds.filter((build) => build.buildId !== targetBuildId)
```

然后将计算页的敌人、Buff、动作参数和反应窗口组成现有 `EvaluationScenario`。切换计算对象只改变请求中的 `primary`，不会改变队伍或配置库。

辅助指标使用相同的目标选择逻辑：目标成员作为指标来源，其他队员作为 `context.teammates`。需要受益对象的辅助指标，在指标自身的上下文区域中从当前队伍选择接收者。

## 装备特效自动解析

装备特效采用统一的 `maximum_reachable` 策略：

- 无条件自身效果自动生效。
- 目标动作必然触发的效果自动生效。
- 可叠层效果按当前角色机制实际可达到的最高层数计算。
- 队伍构成、元素数量、同异元素队友等条件从当前队伍推导。
- 护盾、治疗、生命阈值等前置条件只有在当前队伍或动作可以满足时才启用。
- 无法由当前角色和队伍达到的条件不强行开启。
- 角色技能领域、食物和外部场景 Buff 不归入装备自动特效，继续由计算页配置。

所有伤害基准、单词条边际收益和候选武器比较必须调用同一个装备效果解析入口。候选武器比较流程为：

1. 从目标配置复制一份临时 build。
2. 替换候选武器及目标精炼等级。
3. 根据候选 build、当前队伍和目标动作重新解析装备特效。
4. 重新计算最终面板以及与圣遗物套装联动后的指标结果。

不能复制基准武器的 `activeEffectIds`，也不能让 UI 勾选状态决定候选武器效果。

## 视觉方向

保持白底、黑字、低装饰的工具型界面，重点通过留白、细边框、字号层级和单一强调色表达状态：

- 配置操作使用紧凑的横向按钮栏。
- 配置卡不堆叠武器和圣遗物详情，只呈现角色名、来源和入队状态。
- 当前队伍使用四个等宽坑位；无成员时显示清晰的加号和空状态。
- 计算页把队伍、指标和场景控制放在报告上方，不恢复左侧步骤栏。
- 结果报告采用单列主叙事，严格遵循已确认的展示顺序。
- 桌面端限制内容最大宽度；移动端按钮、配置卡和队伍坑位自然换行。

## 迁移阶段

### 第一阶段：状态与兼容层

- 建立配置库、队伍和计算会话类型。
- 建立带版本的本地存储读写与迁移。
- 扩展 JSON 导入，支持工作空间格式并从旧场景提取全部角色配置。
- 建立由无序队伍和计算对象装配现有请求的适配器。

### 第二阶段：配置页

- 实现配置操作栏、按角色分组的配置库和四个队伍坑位。
- 迁移展示柜、JSON 和手动初始化入口。
- 实现队伍持久化、唯一角色校验和确认跳转。
- 内置默认配置仅提供接口和待维护状态，不批量生成未经确认的默认配置。

### 第三阶段：计算页

- 实现计算对象、指标、敌人和 Buff 选择。
- 接入伤害与辅助指标端点。
- 按确认顺序重排结果报告。
- 移除旧左侧流程和计算页内的角色编辑器。

### 第四阶段：装备特效统一

- 将装备特效从 UI 主动勾选中移除。
- 建立 `maximum_reachable` 解析入口。
- 让基准结果、词条收益、有效词条和候选武器复用相同解析路径。
- 保留角色技能与外部 Buff 的显式场景配置。

### 第五阶段：清理旧结构

- 删除旧 `WorkflowStep`、`SourcePanel` 和以 `scenario.primary` 为中心的页面状态。
- 删除只为旧左侧流程服务的 CSS 和测试。
- 保留兼容导入逻辑，不保留旧页面组件的双轨运行。

## 验证策略

测试以系统行为为主，不为每个角色重复编写 UI 测试：

- 配置库可保存同角色多套配置，导入冲突规则稳定。
- 队伍支持 1–4 人、角色唯一、刷新恢复和删除引用清理。
- 切换计算对象只改变请求主对象，不改变队伍。
- 伤害指标与辅助指标都能从队伍成员发起计算。
- 工作空间导出不包含队伍和场景状态。
- 旧单 build、旧场景和新工作空间 JSON 均可导入。
- 更换武器会为每个候选 build 重新解析武器与圣遗物效果。
- 薙草之稻光的爆发后充能能够进入绝缘之旗印的增伤计算，且基准和候选比较一致。
- 浏览器端到端覆盖“导入配置 → 组成队伍 → 选择成员指标 → 计算 → 返回修改配置”的完整路径。

## 非目标

- 本轮不批量制定全角色内置默认配置。
- 本轮不实现完整循环 DPS 或复杂站场时间线。
- 本轮不赋予队伍坑位战斗顺序语义。
- 本轮不增加单角色导出、队伍导出或计算结果导出。
- 本轮不允许计算页直接编辑完整角色配置。
