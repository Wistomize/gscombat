# ADR-0017：按功能边界组织 Web 客户端

## 状态

已接受

## 背景

`apps/web/app/workbench.tsx` 同时承载 Build 编辑、计算设置、接口请求、公式格式化和全部结果报告，`configuration-workspace.tsx` 同时承载会话、云端同步、导入、配置库和队伍管理。CSS 已有区域划分，但 TSX 边界没有同步形成。

Web 当前只有两个页面，使用 React 本地状态、浏览器存储和邀请会话云同步。此次目标是降低修改影响面和认知负担，不是更换状态管理或重新设计交互。

非功能约束包括：

- 保持服务器组件与客户端组件边界，避免把整个路由树变成客户端渲染；
- 保持云端同步的顺序性、乐观并发和失败恢复；
- 保持现有请求协议、DOM 语义、CSS 类名和中文文案；
- 允许角色、指标和结果类型继续扩展，而不让页面文件线性膨胀。

## 决策

采用按功能切片的模块化前端结构：

- `app` 仅保存 Next.js 路由入口和页面组合；
- `features` 保存 Build 编辑、配置库、队伍、工作空间会话、计算设置和计算报告；
- `components/ui` 保存不理解业务的共享视觉组件；
- `lib` 保存无 React 页面依赖的 API、格式化和工作空间基础设施；
- `test` 保存 Web 包级系统测试与集成测试。

页面级 Controller 继续持有跨区域状态，通过 Props 向下传递。云端同步可以抽取为局部 Hook，但不引入 Redux、Zustand 或第二套全局状态系统。

## 后果

### 正面

- Build 编辑器不再反向依赖计算工作台；
- 新增结果区域或配置入口时只修改对应功能模块；
- 云端同步状态机拥有单一维护位置；
- 路由入口、功能协调、纯展示和基础设施依赖方向清晰；
- 测试不再与生产模块混放。

### 负面

- 组件 Props 数量在第一阶段可能增加；
- 纯结构重构涉及大量文件迁移，需要完整集成回归；
- Controller 在不改变状态模型的约束下仍会保留一定体积。

### 中性

- 现有 CSS 类名和样式文件暂不按功能迁移；
- 本地存储键和云端工作空间文档格式保持不变；
- 后续若确有多页面共享状态需求，需要另行决策，不能由本次重构自动推导。

## 备选方案

### 继续在 `app` 下按通用组件分类

未采用。`build-editor`、`party` 和 `calculation-report` 是业务功能，不是通用组件；全部放入 `app/components` 会弱化所有权，并让路由目录继续承担非路由职责。

### 引入全局状态库后再拆组件

未采用。当前只有两个页面，现有本地状态能够表达需求；同时更换状态模型会扩大行为回归面，尤其影响云端同步和指标切换。

### 只按文件行数机械拆分

未采用。行数不能形成稳定依赖方向，容易产生 `helpers.tsx`、`components.tsx` 等新的杂物模块。
