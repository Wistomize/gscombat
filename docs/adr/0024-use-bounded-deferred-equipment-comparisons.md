# ADR 0024：有界异步装备比较

## 状态

已接受，实施中。范围见 [OpenSpec 设计](../../openspec/changes/compare-artifact-loadouts/design.md)。

## 决策

沿用 [ADR 0014](0014-use-one-authoritative-scenario-metric-evaluation-path.md) 的唯一场景求值链路。
套装比较只覆盖求值期的有效件数，原始主副属性、实际装备和保存格式不变；统一计数入口供基础属性、效果和能力使用。
临时构筑使用内部 Symbol 元数据，普通对象展开保留，JSON 不会持久化。每个候选拥有独立 Build 身份，避免旧派生面板污染。

2＋2 采用 Content 维护的同类代表对，不枚举全部搭配。暴击率四件套比较的新增溢出折算属于显式理论调配，
不是游戏规则：通过事件局部双暴输入干预复用正式求值，基准事件按角色与事件标识匹配；多人贡献仅改装备者。
基准已有溢出、实际配置、武器及边际收益不参与折算，接口返回逐事件折算量供界面说明。

核心报告、武器与套装列表使用独立兼容 HTTP 请求。API 负责有界批次、取消、去重及短期缓存；Analyzer 不依赖网络、鉴权或调度平台。
缓存只作优化，以完整场景及版本识别，服务端基准为准；失效可重算。保持旧完整接口和单武器入口，不迁移用户数据。

## 备选方案与后果

- 改写五件装备会制造虚假库存并可能误保存，因此只覆盖件数。
- 复制伤害公式容易偏离正式计算，因此候选调用同一求值器。
- 持久作业、线程池、分布式缓存增加运维和状态复杂度，当前不引入。
- 单线程批次不能抢占一个候选；须实测核心及健康请求延迟，若单候选过慢，应报告限制而非扩大队列掩盖问题。
- 排名必须保留完整结果池，单项更新只重算该候选，但会重新筛选全榜。只有全池完整时才宣称完整排名。
