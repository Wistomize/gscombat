# ADR 0015：从实体自有声明生成 Content 注册表

## 状态

已采纳。

## 日期

2026-08-06。

## 背景

Content 已经按角色、武器和圣遗物建立目录，但聚合关系仍由多个中央文件人工维护：

- `combat-registry.ts` 手工导入并排列全部角色；
- `combat-action-effects.ts` 手工导入并展开全部装备动作效果；
- `equipment-coverage-ledger.ts` 在一个 Map 中保存完整装备覆盖审计；
- `reviewed-multi-scaling-evidence.ts` 集中保存所有角色的多倍率证据；
- `catalog-presentation.ts` 和 `catalog.ts` 重复保存角色展示信息。

这使“增加一个实体”变成跨目录事务。实体声明、覆盖状态、证据和展示信息能够独立审阅，却要在
无关实体共同修改的文件中登记；随着 117 个角色、234 把武器和 61 套圣遗物持续增长，遗漏、
重复和合并冲突都会线性增加。

## 决策

Content 采用“实体自有声明，构建期静态聚合”的目录约定。

- `characters/<id>` 拥有 definition、combat 和可选 evidence。
- `weapons/<id>` 与 `artifacts/<id>` 拥有 effects、coverage 和 index；没有当前动作效果的实体以
  类型化空数组明确表达，不从目录契约中消失。
- 装备通用类型、缺省状态和发布判定属于共享规则，不复制到各实体。
- 官方中文名、游戏数据 ID、武器类型和个别动作展示覆盖属于角色 definition。
- 一个确定性 Node/TypeScript 工具扫描这些约定文件，生成带显式静态 import 的注册表。
- 生成文件提交到仓库。`--check` 模式重新计算预期内容并在文件缺失或过期时失败；构建、测试和
  类型检查均执行该守卫。
- 运行时代码只导入生成的静态模块，不读取目录、不依赖 glob，也不根据命名约定动态加载模块。
- Content 根入口只导出稳定查询、领域类型和通用规则；单个实体模块不再通过根 barrel 全量暴露。

生成器按目录名稳定发现实体。角色目录展示需要保持产品顺序，因此由各角色 definition 的唯一
`catalogOrder` 显式排序；其他聚合按目录名排序。任何投影都不能依赖文件系统返回顺序或手工 import 顺序。

## 后果

### 正面

- 新增或审阅实体时，主要改动局限在其自身目录和自动生成文件。
- 注册表不再出现手工漏登；目录契约和生成新鲜度可由 CI 机械验证。
- 覆盖原因和倍率证据能够与实现并排审阅，减少跨文件追踪。
- 浏览器与服务端仍得到普通静态 ESM，部署行为和可分析性不变。
- 根入口大小不再随武器和圣遗物数量线性增长。

### 负面

- 仓库会提交生成文件，修改实体后必须运行生成命令。
- 首次迁移会产生大量机械文件移动，需要完整等价基线防止状态或标签漂移。
- 目录约定比自由命名更严格；违反约定会在生成阶段直接失败。

### 中性

- 生成器负责发现和聚合，不负责推导角色机制、装备效果或覆盖结论。
- 中央查询门面可以继续存在以保持公共 API，但不得重新保存实体清单。

## 考虑过的替代方案

### 继续手工维护中央数组和 Map

拒绝。它保留了当前冲突热点，也不能机械证明实体目录与发布目录一致。

### 运行时扫描目录或使用 glob 导入

拒绝。Node、Next.js、Taro 和测试运行器对运行时文件系统及 glob 的处理不同，会把部署差异引入
领域层，并削弱静态类型检查和 tree-shaking。

### 用一个 YAML 或 JSON 总清单生成全部实体文件

拒绝。总清单仍是中央所有权，只是换了格式；角色、装备实现和审阅信息依然分离。

### 不提交生成文件，只在构建时生成

拒绝。这样代码审查无法直接看到注册表变化，本地类型检查也依赖隐式前置步骤。提交生成物并用
`--check` 校验既保持可审阅性，也能阻止陈旧文件进入主线。
