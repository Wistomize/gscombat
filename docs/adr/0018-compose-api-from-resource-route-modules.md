# ADR-0018：按资源路由模块装配 API

## 状态

已接受

## 背景

`apps/api/src/app.ts` 同时创建 Fastify 和共享资源、注册 16 个路由，并负责 Catalog、战斗覆盖、分析和辅助指标响应的深复制。它已经成为 883 行的组合热点，路由生命周期和序列化细节互相遮蔽。

本次调整必须保持公开 HTTP 契约、邀请码会话、SQLite 工作空间、展示柜导入及计算结果不变，也不能引入自动路由扫描或新的运行时框架。

## 决策

- 保留单体 Fastify 服务和显式装配。
- `app.ts` 只创建资源、注册关闭钩子并按固定次序装配路由。
- 路由按 `session-workspace`、`catalog-audit`、`analysis`、`showcase` 四个资源边界维护。
- 路由注册函数通过窄参数接收所需依赖，不读取全局服务定位器。
- 响应投影进入 `serializers/`，工作空间、展示柜和动作效果实现进入 `services/`。
- 测试进入包根 `test/`，结构守卫阻止路由和测试重新膨胀到组合根。

## 影响

### 正面

- 路由、序列化和基础设施可以独立阅读与验证。
- `buildApp` 仍是唯一应用创建入口，部署方式不变。
- 显式依赖和装配次序使资源生命周期清晰，没有隐式扫描。

### 负面

- 文件数量增加，跨模块修改需要明确选择资源边界。
- `app.ts` 为兼容已有调用方继续重新导出四个序列化函数。

### 中性

- 本次不统一 Web 与 API 的 Catalog 投影；该问题继续由 ARCH-007 处理。
- 服务仍是单进程 Fastify 与 SQLite，没有引入额外部署单元。

## 备选方案

### 只把 `buildApp` 切成几个私有函数

可以减少单个函数长度，但序列化和路由仍集中在同一文件，无法形成稳定边界。

### 使用 Fastify 自动插件扫描

文件更少显式装配代码，但引入发现规则和启动期隐式行为；当前 16 个路由不需要这项复杂度。

### 拆成多个服务

会增加部署、网络和一致性成本，当前问题只是单体内部组织，不是容量或隔离问题。
