## Context

动机见 [proposal.md](proposal.md)。基于主线 `6cc223f5162a98d05fa8fb7ba49c4d6a8aa4df96`：

- Web `changeWeaponComparisonRefinement` 调用完整 `runAnalysis`；API 先 `evaluateScenario`，随后 `analyzeScenario` 又求一次基线。
- `analyzeWeapons` 把候选构造、资格筛选、条件迁移与求值放在全量遍历中，没有单候选公开能力。
- 多参与者特殊反应在 `direct.ts` 中为每个参与者调用 `resolveScenarioActionEffectContext`，重复求整队来源属性；其后实际使用的是外层真实动作上下文的来源映射。
- `GameDataRepository` 在热点 getter 每次 prepare SQL，并反复解析同一只读 JSON。

上一轮本地代表性样本：四人梦见月冰风旋指标，46 把武器、11 个词条和 2 个成长项；单动作约 0.35 秒，完整分析约 22 秒，再改一把精炼仍全量重算约 32 秒。它们是少量观测，第一次完整分析带 CPU profiler，不能把差异解释为精炼的额外开销，也不是生产 SLO。后续需统一环境重建基准；此前没有保存可复用的原始 profile 文件。

## Goals / Non-Goals

**Goals:** 局部精炼请求成本与候选总数解耦；首次完整分析减少准备成本；数值、来源轨迹、前后台资格以及请求间隔离不变。

**Non-Goals:** 不跳过队友、不改变暴击组合枚举、不建立跨场景最终属性缓存，不给同步 Node 计算添加伪并行，不顺带做错误码总治理。辅助指标不新增武器比较。

## Decisions

### 1. 同一分析资源增加无状态单候选子入口

采用 `POST /v1/analysis/weapon-comparison`：请求 `{ scenario, weaponId, refinement }`；scenario 复用完整 EvaluationScenario 契约，不包含全量候选精炼覆盖表。响应 `{ baselineExpectedDamage, weapon }`，weapon 复用完整分析已有武器结果字段，不复制独立类型。新 Schema 与类型只从 Contracts 包根公开。

Analyzer 提取私有的单候选构造/资格/求值函数，供全量遍历和新增包根单候选入口共同使用。合法局部请求执行基线及指定候选两次场景求值，不跑全部武器、词条、成长项。维持现有候选等级 90/突破 6、精炼默认与覆盖规则、来源绑定、可达效果及零基线收益比例约定；局部请求明确提供精炼 1–5。

API 仍由现有分析 route module 装配，沿用指标命座校验；候选输入/资格错误返回 400，真实计算异常不吞掉。服务端不接收客户端数值基线，不依赖邀请码或报告 token。完整 `/v1/analysis` 兼容不变。

备选：在完整接口增加返回模式会使原响应变成联合类型，增加兼容负担；保存报告 token/缓存整个场景会引入淘汰、版本、隐私和实例间同步，因此暂不采用。

依赖保持 Web → Contracts/HTTP，API → Analyzer 包根与 Contracts，Analyzer → Content/GameData/Calculator。长期边界见 [ADR-0021（提案）](../../../docs/adr/0021-use-stateless-incremental-weapon-comparison.md)，承接 [ADR-0014](../../../docs/adr/0014-use-one-authoritative-scenario-metric-evaluation-path.md) 和 [ADR-0018](../../../docs/adr/0018-compose-api-from-resource-route-modules.md)。

### 2. Web 按报告世代和武器维护局部请求

成功生成完整报告时持有与之对应的不可变提交场景快照，而非从当前表单临时拼装旧报告的局部请求。配置、指标、敌人、Buff 变化立即使旧世代失效；重新开始完整分析、返回配置及卸载同样失效。

完整请求维护序号，武器请求使用「报告世代 + 武器 ID + 该武器请求序号」。仅最新合法响应可写入。按 weaponId 函数式合并结果后重排，保留其他完整报告字段；不同武器独立合并，同武器旧响应无效。AbortController 取消过期网络等待，但正确性依赖序号而非取消；不声称它能终止已开始的服务端同步运算。

行状态区分成功精炼/数值与待选择精炼；等待时保留旧结果并明确标注，失败后恢复上次成功精炼且允许重试。完整报告尚未就绪或场景已失效时不发局部请求。同值且无待处理变更直接跳过。响应基线若与原报告不一致，不混合两个版本的结果，提示重新完整计算。

### 3. 固定数据缓存归只读仓库实例所有

在 GameDataRepository 内复用固定 SQL 的预编译 statement。优先缓存被 profile 指出的角色记录、曲线属性、技能参数组、武器属性与 manifest，不一次性复制整库，也不引入通用缓存框架。

结果缓存使用完整查询参数元组作为键，按实例设置总上限（初始 4096 项，可由基准调整而不改变外部行为）；不得把任意无效输入无限保存。标量直接返回，复合对象保留内部快照并向调用者返回副本，避免可变别名跨请求污染；即便 TypeScript 声明 readonly，也不得只靠类型保证安全。

仓库对应一个固定数据库，关闭时清理缓存和 statement 引用，关闭后读取仍失败；不同数据库实例绝不共享缓存。更新固定数据通过新仓库/进程生效，不引入运行中热切换。用户工作区 SQLite 不参与该缓存。

### 4. 场景准备拆分只复用同一变体的来源映射

将共享 action effect context 拆为「真实动作所有者的整队来源属性」与「当前参与者的基础属性、元素及合法效果选择」。原通用入口组合这两部分；多参与者求值只准备一次真实动作来源映射，再为各参与者准备后者。

角色身份、输入 deltas 接收者、显式来源绑定、精通分享前后快照及前后台资格必须保持原样。不能把参与者临时视作真正的动作所有者。此约束承接 [ADR-0020](../../../docs/adr/0020-preserve-explicit-event-effect-eligibility.md)。复用边界是同一个完整场景变体，武器/精炼/词条/等级改变后重新计算来源映射，确保千夜浮梦等团队装备重新影响所有合法参与者。

完整 API 的双基线问题通过 Analyzer 内部组合入口一次性产生 evaluation 与 analysis；`analyzeScenario` 现有包根调用保持兼容。不得公开一个允许 HTTP 提供任意预计算基线的捷径。

### 5. 分阶段验证，不扩张角色测试矩阵

先保存固定输入及旧链路输出，再分别交付单候选链路、只读数据复用、来源准备去重。每阶段比较同一输入的基线、候选、事件结果与来源轨迹；不以更新期望值掩盖差异。

少量组合覆盖普通直伤、梦见月风/冰反应、合法与互斥的来源前台状态、团队增益武器；C1/C6 与暴击上限优先复用已有用例。HTTP 使用真实 SQLite 和完整应用组合根，Web 请求乱序可控地验证状态合并。

性能探针记录 Node/快照/版本、输入、冷启动与预热情况；统一预热后做 3 次采样取中位数，对比单指标、完整报告及局部精炼。确定性验证工作量：局部仅基线+一个候选，不遍历全量比较；来源准备不随参与者重复。耗时不设脆弱 CI 阈值，必须实测报告改善或残留瓶颈；不增加常态生产遥测和完整敏感请求日志。

## Risks / Trade-offs

- 多参与者来源映射重用可能改变受益方 → 将真实动作所有者与参与者显式分离，用现有前后台正反例及带队伍增益武器差分验证。
- 缓存可变对象/无效参数导致污染或增长 → 对象副本、实例边界、完整键和有界淘汰；关闭后行为验证。
- 连续选择精炼仍会启动已收到的服务器计算 → 客户端取消和序号保证正确性，不冒充服务器取消；本次首先消除全量放大。
- 全量第一次计算仍遍历武器 → 共享准备降本后实测；任务队列/工作线程留到证据证明必要时单独设计。
- API/Web 部署短暂版本不同 → 先 API 后 Web；局部接口失败不偷偷退回昂贵全量分析，保留报告并提示失败。

## Migration Plan

无数据迁移。实现后记录数值一致性与性能证据，获得发布授权后先部署兼容旧 Web 的 API，再部署新 Web。需要回滚时先回 Web 再回 API，数据挂载保持不变。本次提案不执行提交、推送、部署或归档。
