## Context

动机与范围见 [proposal.md](proposal.md)，逐武器裁决见 [确认记录](../../../docs/plans/2026-09-17-weapon-effect-review.md)。以下 Context 保留实施前观察；当前完成状态见 [tasks.md](tasks.md) 与 [audit.md](audit.md)，不以“已确认”代替验证。

2026-09-27 已检查的实现事实：

- `analysis/analyze.ts#getCandidateActiveEffects` 在候选侧按 `weaponComparisonDefault` 增补并覆盖互斥组选项；实际基准没有由该函数应用默认值。旧设计明确要求“不改变基线”，与本轮目标不同。
- 完整与单候选比较已经共用 `prepareWeaponCandidate` / `evaluateWeaponCandidate`，继续复用，不另建求值器。
- `scenario/capabilities.ts` 已有治疗/护盾对象、反应资格、E 施放/命中机会及祭礼重置；机会函数目前使用固定的 0.3 秒命中间隔门槛，不能直接代表所有武器的 0.1/0.2/0.3 秒要求。
- `scenario/effect-lifecycle.ts` 已区分触发、退场保留、实时前后台和受益者，允许准备查询使用来源前台，但不改变实际命中上下文。
- 完整请求目前只附带精炼覆盖；单候选请求仅有 scenario/weaponId/refinement，尚无独立候选条件覆盖。网页已有单行增量请求与过期响应保护。
- 当前实现候选限制四/五星、90 级六突破；用户已修正目标为三/四/五星均可比较，本轮需移除三星排除条件。特殊武器合法等级需要显式资格，不能只因没有 90 级数据就静默消失。

以上是关键路径检查，尚不是 233 把的逐项代码差异审计。阶段 1 必须补齐差异清单后才改声明。

## Goals / Non-Goals

**Goals:** 在现有声明及资格系统上完成本轮规则迁移；可定位每把武器的实现与验证状态；候选与基准同语义、来源隔离、单行更新。

**Non-Goals:** 不造通用规则语言、时间线引擎、全局可变战斗状态、另一套武器评分或庞大中央武器分支。无需为每把武器写一套模拟公式的单元测试。排除项、数据更新及发布边界见 proposal。

## Decisions

### 1. 实体声明为唯一运行时规则来源

复用 `content/src/weapons/<slug>/{effects,coverage,index}.ts`；只有过长时拆实体局部 helper。用户特例（甘雨阿莫斯、菲谢尔幽夜、温迪黎明、克洛琳德赦罪等）留在对应实体声明，不能散入 Analyzer、Web 或 Calculator。

`content/src/combat/{types,capabilities}.ts` 仅补可复用字段，生成注册表继续由工具聚合。规则记录是决策证据，不在运行时解析 Markdown；coverage 是代码覆盖事实，不因规则已获同意就标记 implemented。

遵循 [ADR-0014](../../../docs/adr/0014-use-one-authoritative-scenario-metric-evaluation-path.md)、[ADR-0015](../../../docs/adr/0015-generate-content-registries-from-entity-owned-declarations.md)、[ADR-0021](../../../docs/adr/0021-use-stateless-incremental-weapon-comparison.md)、[ADR-0022](../../../docs/adr/0022-preserve-scenario-field-identity.md)、[ADR-0023](../../../docs/adr/0023-declare-effect-field-lifecycle.md)。不新增架构边界，无需另造 ADR；实施同步已有 ADR 中武器迁移状态即可。

### 2. 统一默认解析，不让候选补 Buff

在现有 `effects/effect-selection.ts` 的规范化边界收敛规则，必要时拆出 `effects/weapon-state.ts`（建议新文件）。保留 `analyze.ts` 的候选资格、替换与排序职责，但逐步删除候选专用默认叠加分支及无消费者的旧默认类型。

处理顺序：规范化旧选择 → 定位来源/受益者与实际前台 → 验证不可绕过资格 → 采用有效显式选择或声明默认 → 成组应用效果 → 原有属性与事件流水线。内部选择键至少区分 sourceBuildId、weaponId、选项组；同一状态的生命/精通等效果一次性整体解析，不能互相覆盖。

自动状态不受旧显式开关控制；必要手选的有效零值/关闭值优先于默认。来源门禁先于手选，不能通过选择让非魔导角色或后台来源越权。候选先替换 Build，再派生能力与状态，保留所有合法队友来源，不回写输入。

伤害、多人反应贡献、来源面板和辅助指标共享资格；辅助指标仍不提供伤害排名。新增默认准备的来源说明复用当前公式轨迹，不增加对比列表状态栏。

### 3. 只补有本轮消费者的能力缺口

| 能力 | 已有基础 | 本轮补齐与代表消费者 |
| --- | --- | --- |
| 治疗/护盾来源与对象 | 能力、来源、受益方、前后台 | 金珀等装备治疗；受疗与主动治疗两种路径；海渊、流华、钻机、盾系列 |
| 命中/施放机会 | 冷却、充能、连段、重置、有限命中证据 | 将叠层窗口、最小间隔作为查询要求；必要时表达独立到期/续层的有限准备策略；白湖、圣祭、神乐，不推演循环 |
| 指定反应触发 | 已有反应族与元素参与 | 武器列举反应的精确集合，区分队伍能触发/本人能触发/本人可造成特殊反应伤害 |
| 角色与队伍资格 | 月兆、夜魂、魔导、旅行者变体 | 各来源分别检查，不能借队友夜魂或魔导资格；特殊能量显式语义，未知不等于零 |
| 特定准备来源 | 命中、生命变化、附魔等现有声明 | 仅为白雨、聊聊棒、筑云等确认条款补所需生命之契获得、自附着对象、合法扣能准备事实；缺证据不用“能放技能”替代 |
| 属性关联与接力 | 现有 final_hp/final_attack/EM 转换、来源映射 | 重算后取值、合法二次转换限制、共享唯一接力对象及同名不叠加；不新增通用递归求解器 |

新增字段逐一绑定消费者和真实角色/装备证据；禁止无依据给全角色批量“有能力”。准备次数不能变成伤害事件次数；受伤、主动扣血、低血和生命上限变化不可相互替代。某武器的工具默认仅是局部假设，例如苇海无盾不改变全局盾事实。

### 4. 条件输入与候选覆盖

沿用现有 activeEffectIds/source 映射兼容实际装备输入；Content 提供语义化选项组（稳定选项 ID、可选值、默认值和适用性）。Web 不硬编码数值或角色规则。只为当前无法表达的必要选择添加最小契约；不把自动资格保存成 Build 字段。

完整分析增加可选 `weaponComparisonChoices`，按候选 weaponId 保存选择；单候选增加可选 `choices`，使用相同 TypeBox 选择契约。选择通过源装备者、武器、组和值解析到合法效果，而不是允许客户端注入任意 effectId 或数值。具体值集合由目录投影提供；API 验证组归属、层数和接力对象。

候选专属覆盖仅作用于候选，不改变 baseline。共同场景选择（本次箭命中要害、敌人状态、实际前台等）不伪装成单武器私有状态；改变这些输入应重新分析相关结果。上一次报告的场景保持冻结，候选选择/精炼计入行缓存键和请求世代。

没有条件的旧请求继续使用新默认。被废弃的自动化开关可解析但不强制生效；仍有效手选保留。已知旧 ID 明确映射，不一律忽略未知输入。来源不明确时沿用当前显式选来源要求，不任选一个角色。

### 5. 对比资格与特殊等级

实际装备条件目录请求增加可选 `supportMetricId`，用于区分复用伤害 `sourceActionId` 的辅助指标；省略时保持伤害目录行为。API 必须验证角色、指标、来源动作和最低命座，不接受任意动作冒充辅助指标。辅助目录与现有辅助求值共用 `resolveSupportFieldContext`，未指定前台时不假定来源在场。只投影现有辅助来源面板消费的自有属性选择组，纯伤害或队友伤害转发组不显示；相关组保留完整选项，允许选中对该指标无收益的有效变体。页面共用实际装备条件区域，不新增辅助武器对比。明确的非法前台成员及伤害前后台冲突在目录入口返回 400，不捕获并伪装内部错误。

用户后续确认宗室五把武器全部不列对比，使用既有实体 `comparison.excluded` 策略，完整与单候选入口共用；不在前端另设隐藏名单，不删除武器目录或旧角色配置。保留的旧层数逻辑不等于已支持多段清层，本轮不扩展此模型。

比较池包含已支持、类型匹配的三/四/五星武器，完整列表和单候选入口使用同一资格。普通候选沿用 90 级六突破，三星与四星默认精炼 5，五星默认精炼 1；均保留合法精炼选择，不偷偷把当前低级武器当成同级对比。精炼锁定武器只展示合法精炼。星锋剑等特殊武器的默认共鸣由实体决定，不用精炼字段冒充共鸣。一/二星与既有排除项仍不纳入。

实施前核实共鸣四级允许的等级及当前固定版本可解锁旅行者元素，绑定可追溯参数。若合法候选不是 90 级，候选构造使用其合法等级，并让现有行名称附近或等级字段显示这一差异；不得生成非法配置或静默用 90 级。若证据仍不足，只阻塞该条目的验收，其他批次继续，不伪造满覆盖。

### 6. 批次与测试预算

顺序为：逐项差异清单 → 统一入口最小纵切 → 条件能力与公共选择 → 按机制迁移声明 → Web/契约完整收口 → 集中回归。纯实体批次可以独立验证，但所有武器归属一个主批次，复杂条款可引用先前能力。

每个规则族用参数化表验证声明覆盖、默认、门禁和必要负例；端到端以真实 Content/Analyzer/SQLite/API 路由和网页交互为主。233 行清单核查不等于新增 233 个重型测试。每批只跑相关集成测试；末尾集中跑一次全仓 gates。

至少保留：同武器相同配置零收益；实际装备=候选；全量=单候选；无治疗/适用治疗/队友仅自疗；前后台与多人贡献；相同武器多来源；普通/特殊反应分区；合法精炼边界；换武器引起套装/队友资格变化；一行更新不全榜重算。

## Risks / Trade-offs

- [规则已确认但代码覆盖不齐] → 差异清单区分无需改动、声明迁移、能力缺口、明确排除；每项关联代码和验证证据。
- [已有正确武器被通用默认改变] → 小纵切先验证，新旧解析不能双重计入；分批复查同来源互斥与后台条件。
- [静态能力不能证明整队轮转] → 只实现已确认准备口径；不推广成实际治疗量、元素附着或窗口覆盖率。
- [属性依赖和装备治疗形成自证循环] → 能力先按静态配置/合法动作建立，禁止以自己授予的 Buff 证明自身触发；属性转换沿用现有排除规则。
- [默认变化令旧结果下降] → 在规则及轨迹中说明，不把测试期望改回错误旧值；对既有失败先记录原因。
- [性能回退] → 同一候选复用规则上下文，贡献者只改变受益者视角；不跨候选复用最终面板、不递归全量分析。
- [工作区已有未提交改动] → 阶段 1 记录基线；重叠 Web 文件人工审 diff，不能清掉圣遗物和图标改动。

## Migration Plan

### 实施补充：事件与来源身份

- 必要选择目录按实际附魔后的有效元素与本体元素分别筛选；依赖效果解析提取为轻量模块，目录不调用伤害计算器。
- `prepared_stack_refinement_table` 用于雾切的独立准备条件；已核验的爆发取面板例外声明在角色动作中，不在武器里维护中央角色分支。
- 普通与混合动作都按事件解析箭矢限定/消耗效果，并在报告携带可选逐事件属性来源；未命中的零次数事件不消耗效果。
- 辰砂、裁断只有已声明的时刻才能证明消费窗口/重触发。无间隔证据的聚合多击仅首击计入准备效果，剩余击不虚构冷却刷新；这不是轮转模拟。
- 产球拾取自疗作为装备能力，检查实际前台及已核验产球来源；不增加武器治疗数值或实际拾球事件。

1. 保持旧 JSON/场景可读，建立有界旧 ID 映射；不改 SQLite 表、角色库版本或清理用户数据。
2. 新条件字段均可选；API 与 Web 同版本发布，API 先具备新字段再启用客户端。不得要求用户重新导入全部配置。
3. 升级已有分析语义版本与客户端缓存签名，丢弃旧报告及过期请求，不删除角色配置。
   单候选响应追加向后兼容的可选 `engineVersion`；新客户端拒绝把不同版本的候选合入旧报告，即使基准值恰好没变。报告仅驻留当前页面内存，无持久化用户数据迁移。
4. 所有批次通过后才请求提交/部署授权；发布前备份工作区，回滚匹配版本的 API/Web 与分析缓存版本。
5. 撤除失去消费者的候选专用默认实现，而非永久保留双系统。保留必要旧输入映射并明确其兼容职责。
